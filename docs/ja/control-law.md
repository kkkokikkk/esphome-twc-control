## 1. 全体の流れ

```
Shelly Pro 3EM（主幹。車の分岐も含めて測る）── 1秒
        │  HA 経由でミラー
        ▼
  real_a/b/c（アンチグリッチ済みの実電流）
        │
        ├──► signed_a/b/c      符号付き（＋買電 / −売電）
        │         │
        │         ├──► household_x = signed_x − vitals_x    ← 車を引いた「家だけ」の信号
        │         │         └──► desired_avail              ← 目標（＝車に許してよい量）
        │         │
        │         └──► corr_x = max(signed_x, vitals_x)     ← 相関用（車を下回らせない）
        │                   └──► worst = max(corr_a,b,c)
        ▼
TWC3 の /api/1/vitals ── 2秒 ──► vitals_current_a/b/c, vehicle_current, contactor_closed

  o_raw = car_charging ? (worst + bias_offset) : bias_offset
          ただし bias_offset = twc_breaker − desired_avail
        │
        ▼
  pub（制限値超過分を圧縮・上限付き）＋ ディザ ±0.05A
        │
        ▼
  Modbus レジスタ 0xF4〜0xFC に **3相とも同じ値**を書く
        │
        ▼
      TWC3 が車を絞る
```

## 2. なぜ「利用可能電流を計算して渡す」ではないのか

**TWC3 FW 26.26.1 は、自分に設定されたブレーカー制限（`twc_breaker_limit_a`）より下では、報告値を一切見ていない。** 何を報告しようと自分の内部上限まで充電する。

**制限値を超えた分だけが制御信号になる。** 実測された反応マージンは **`twc_breaker_limit_a` + 約 1.1〜1.2A**。

→ だから「正確な利用可能量を計算する」系の設計は全部無効。**公表則（publication law）＝「制限値をどれだけ超えて見せるか」を決める規則**になっている。

## 3. 主要な変数

| 変数 | 意味 |
|---|---|
| `twc_breaker` | `twc_breaker_limit_a`。**Tesla 施工メニューで TWC3 に設定した値と厳密に一致させること**。ずれると制限がずれる |
| `real_a/b/c` | Shelly の実電流（アンチグリッチ済み） |
| `signed_a/b/c` | 符号付き。**＋が買電、−が売電**。売電側は `floor` で切り捨て（余剰を過大に主張しないため） |
| `vitals_current_a/b/c` | **TWC3 自身が測っている車の相ごと電流**（2 秒ごと） |
| `household_x` | `signed_x − vitals_x`。**車を引いた「家だけ」の信号** |
| `desired_avail` | **目標**＝車に許してよい電流。FVE モードでは家だけの信号から算出 |
| `corr_x` | `max(signed_x, vitals_x)`（充電中のみ）。**相関用の項** |
| `worst` | `max(corr_a, corr_b, corr_c)`。**最悪相** |
| `bias_offset` | `twc_breaker − desired_avail`。**「どれだけ下駄を履かせるか」** |
| `o_raw` | 圧縮前の生の公表値 |
| `pub` | 最終的に公表する値 |

## 4. 中核の 3 行

```cpp
float worst       = std::max(std::max(corr_a, corr_b), corr_c);
float bias_offset = twc_breaker - desired_avail;
float o_raw       = car_charging ? (worst + bias_offset) : bias_offset;
```

**読み方**：

- **`bias_offset` が制御そのもの**。目標（`desired_avail`）が小さいほど下駄が高くなり、公表値が制限値を超えて TWC3 が絞る
- **`worst` は相関のためだけに足している**。充電中は、公表値が TWC3 自身のランプに 1:1 で追従しなければならない（後述）
- **アイドル中は `worst` を足さない**。足すと家庭のベースラインを二重計上して、公表値が不必要に低くなる。**実際にそれで充電開始が遅くなるバグがあった**（8A/相 の余剰があるのに 4A しか公表せず、1A→7A と鈍く立ち上がった）

## 5. なぜ `corr_x = max(signed_x, vitals_x)` なのか（R1 ハードフロア）

**TWC3 は「報告された電力計の値が、自分自身の出力と相関しているか」を継続的に検査している。**

物理的な根拠：**引込口の本物の電力計は、充電器の分岐も物理的に含んで測る。だから充電器が引けば、電力計の値も必ず増えるはず。**

**増えなければ「この電力計は嘘をついている」と判断し、`不信状態`（distrust）にラッチして電力計を完全に無視する。**

→ **`max()` で、公表値が車自身の電流を決して下回らないようにしている。** `max` は押し上げる方向にしか効かないので、**「上がるときは即座、下がるときは実測に従う」という非対称性が構造的に保証される**。

### ⚠ ここに罠があった（修正済み・コメントに詳しい）

**R1 フロアを `signed_x` 自体に適用してはいけない。** そうすると：

```
車が電流を引く → signed_x が vitals_x まで押し上げられる
              → household_x = signed_x − vitals_x が ≒0 に潰れる
              → 実際には太陽光が余っているのに予算が消える
              → 充電がまったく立ち上がらない
```

**車が自分の予算から自分を打ち消してしまう。** だから `household_x` は **R1 フロアを通していない生の `signed_x`** から作る。

## 6. `desired_avail`（目標）の作り方

**FVE モード（余剰追従）**：

| 課金方式 | 計算 |
|---|---|
| 相ごと精算（既定） | **最弱相**：`min(−household_a, −household_b, −household_c)` ＋ 手動オフセット |
| 合算精算 | **3 相の平均** |

`−household_x` ＝ 売電していれば正（その分だけ車に回せる）。

**GRID モード**：`desired_avail = twc_breaker`（ブレーカーが許す最大）。

### スルーレート制限（非対称）

```
下降 1.0 A/秒   ← 慎重に（測定のズレ・ノイズ対策）
上昇 10.0 A/秒  ← 速く（雲が抜けたのに絞られたままにしない）
```

**⚠ 主幹ブレーカー保護はスルーの「後」に、即座に適用する**（安全上の上限なので遅らせない）。

## 7. 制限値を超えた後の圧縮

```cpp
excess_gain: 0.75      // 超過分を圧縮する係数
excess_max_a: 1.2      // 制限値からの上振れの上限（実測の反応マージン 1.1〜1.2A に近く保つ）
law_nudge_min_a: 1.1   // 超過しているとき、最低でもこれだけは超えさせる
```

**⚠ 「減衰テール（decaying tail）」は実装しないこと。** 上流の参照プロジェクト（tesla-loadpilot）の**ドキュメントには書いてあるが、実際のコードには存在しない**。PVi1 が一度ドキュメント通りに実装して**実害が出た**：公表値が 1 ステップで制限値を 2A 以上超え、`excess_max_a` を大きく踏み越え、**多相が急に入る起動の窓で TWC3 がセッションを中断（コンタクタ開放）したと見られる**。削除済み。

## 8. エスカレーション（2 段）

制限値を超えたまま時間が経ったとき：

| 経過 | 動作 |
|---|---|
| `escalation_timeout_ms`（既定 120 秒） | `max(pub, twc_breaker + law_nudge_min_a)` へ強制 |
| その 2 倍 | `escalation_kick_a`（既定 1.5A）へ強制 |

**⚠ エスカレーションは電力計が信頼されている間しか効かない。** 不信状態では実測で 8 分間無視された。

## 9. ゾーンステアリング（任意・段階的な制動）

**単一の連続的な超過値では「速すぎて停止させる」か「遅すぎて効かない」かの二択になる**ため、4 つの離散バンドで段階的に効かせる。

| バンド | 公表値 | 意味 |
|---|---|---|
| INCREASE | `limit − 1.0A` | 制限値未満の追従に戻す |
| HOLD | `limit + 0.2A` | **反応させないが、値は動かす**（相関上安全） |
| SLOW | `limit + 0.9〜1.0A` | **高速カスケード帯より意図的に下**。車に下りる時間を与える |
| HARD | `limit + 1.1A` | **確認済みの高速帯**。本物の持続的超過にだけ使う |

**最小滞留ゲート**（既定 3 秒）：バンド境界をまたいでジッタすると、**TWC3 自身の「持続超過」タイマーが毎回リセットされて補正が効かなくなる**。緩める方向は即時、**厳しくする方向だけ**ゲートする。

## 10. フェイルセーフ

```cpp
if (shelly_stale || !ha_api_connected) {
  reported = twc_breaker + dither;   // ＝ 車に 0A
}
```

**HA が落ちる／ミラーのエンティティが古くなる → 充電を止める。** 古いデータで充電を続けない。

**⚠ 可用性の判定は「HA 自身が報告する `unavailable`/`unknown`」で行い、固定の無更新タイムアウトでは行わない。** タイムアウトでは「Shelly が落ちた」と「負荷が変化していないだけ」を区別できず、**負荷が本当に安定しているときに誤検出した**。

## 11. ディザと対称公表

```cpp
pub = std::max(pub + dither, 0.0f);          // ±0.05A を 1Hz で交互に
reported_a = reported_b = reported_c = pub;  // 3相すべてに同じ値
```

- **ディザ**：公表値が長く完全に静的にならないようにする（**本物の電力計は静止しない**）。フェイルセーフ中も止めない
- **対称公表**：TWC3 のサービスループは `min == mean == max` を期待する。**実際にどの相が最弱かに関わらず、真の制約点で正しく係合させるため**

## 12. デバッグの武器：CSV ログ

`recompute_ct` は毎サイクル、内部変数をすべて CSV 形式で `ESP_LOGI` に吐く。

```
ts_ms, mode, real_a/b/c, signed_a/b/c, corr_a/b/c, household_a/b/c,
desired_avail, worst, o_raw, pub, fve_offset_kw,
vitals_a/b/c, vitals_vehicle, contactor_closed, car_charging, grace_active
```

**ブリングアップではこれをそのまま記録に使える。** ヘッダは 5 分ごとに再送されるので、途中からログを拾っても列がわかる。

**⚠ ただしログレベルを VERBOSE にすると Modbus のタイミングが壊れる**（応答期限が約 66ms しかない）。上流の既定は `INFO`。**上げないこと。**

## 14. 実装済み：遅いメーター向けの相関項再構成（項目 1）

### 何が問題だったか

`corr_x = max(signed_x, vitals_x)` は、**`signed_x` 自体が車のランプと一緒に動く**ことを前提にしている。Shelly は 1 秒なので成り立つ。

**本件のメーターは 30〜60 秒。** すると：

```
家庭負荷 > 車の電流  のとき  max() は古い signed_x を選ぶ
  → 公表値が TWC3 のランプを反響しなくなる
  → 不信の突入経路 #2（ランプが平坦な公表値に吸収される）
  → ラッチする
```

### どう直したか

**メーターの新しいサンプルが届いた瞬間に、`signed_x` と `vitals_x` を「同時刻のペア」として捕まえ、その差＝家庭分だけをスナップショットとして保持する。**

```cpp
// メーターの新サンプル到着時だけ更新（meter_seq で検出）
household_snap_x = signed_x - vitals_x;   // 同時刻の 2 値の差 ＝ 純粋な家庭分

// 公表時は、保持した家庭分に「今の車」を足して総量を作り直す
corr_x = household_snap_x + vitals_now_x;
corr_x = max(corr_x, vitals_now_x);       // R1 不変条件は維持
```

**これで家庭負荷の大小に関わらず、公表値は常に vitals の周期（2 秒）で車のランプを 1:1 追従する。**

**副産物**：`household_x`（→`desired_avail`）も改善する。従来は「1 分前の総量」から「今の車」を引いていたので、**古い総量が含んでいなかった量を引いてしまう**誤りがあった。スナップショットにはその誤りが無い（残るのは純粋な古さだけ）。

### 切り替え方

**ランタイムの switch。再書き込み不要。**

| エンティティ | 既定 | 意味 |
|---|---|---|
| `switch.*_slow_meter_correlation` | **OFF** | OFF ＝ 上流のまま。ON ＝ 再構成を使う |

**既定を OFF にしてある理由**：**どちらが実機で良いかは未測定**だから。新規に書き込んだ機体が、いきなり未検証の制御則で走らないようにする。**段階 2 で両方試して決める。**

### 安全装置

**vitals が古いときは自動的に上流方式へ戻る**（`twc_vitals_stale_ms`、既定 6 秒＝2 秒ポーリングの 3 倍）。

理由：**再構成は vitals を「足す」ので、古い値だと二重計上になる**（スナップショットが既にその時点の車を含んでいるため）。一方 `max()` は押し上げる方向にしか効かないので、古い入力でも安全。

そのために **vitals の鮮度スタンプ（`twc_vitals_last_ok_ms`）を新設した。** 上流には無い——上流では vitals が `max()` のフロアにしか使われず、古くても「フロアが上がらない」だけで害が無かったため。
